# Backend — تطبيق الدردشة النصية/الصوتية/المرئية

## المتطلبات
- Node.js 20+
- PostgreSQL 15+

## التشغيل محليًا
```bash
npm install
cp .env.example .env   # ثم عدّل القيم (كلمات السر، مفاتيح مزود الدفع، إلخ)
npm run migration:run  # ينشئ المخطط في قاعدة تبادل
npm run start:dev
```
الـ API يعمل افتراضيًا على: `http://localhost:3000/api/v1`

## قاعدة البيانات والـ migrations

المخطط الأولي موجود في `src/migrations/1794268800000-InitialSchema.ts`،
ويُنشئ الجداول الأربعة، وقيود التحقق، والفهارس، ومُحفِّزًا يمنع تعديل أو حذف
سجلات `wallet_transactions`.

```bash
npm run migration:run      # تطبيق الـ migrations على قاعدة البيانات
npm run migration:show     # عرض الحالة
npm run migration:revert   # التراجع عن آخر migration (احذر في الإنتاج)
```

`DB_SYNCHRONIZE` مغلق افتراضيًا. لا تفعّله إلا على قاعدة بيانات محلية قابلة
للإتلاف. يمكن ضبط `DB_MIGRATIONS_RUN=true` لتشغيل الـ migrations تلقائيًا عند
إقلاع الخدمة، لكن يفضّل تشغيلها كخطوة منفصلة في خط أنابيب النشر.
عيّن `CORS_ORIGIN` في الإنتاج؛ بدونها تُرفض طلبات cross-origin.

## هيكل المشروع
```
src/
  entities/          نماذج قاعدة البيانات (User, KycDocument, WalletTransaction, Room)
  modules/
    auth/             تسجيل / دخول (يفرض شرط السن 18+ عند التسجيل والتوثيق)
    documents/        رفع ومراجعة وثائق التوثيق (KYC) - المراجعة حصريًا من المسير
    wallet/           سجل العملات الداخلية + تكامل بوابة دفع مرخّصة (وليس محفظة شخصية)
    rooms/            إنشاء وإدارة الغرف
    chat/             WebSocket: دردشة نصية + إشارات WebRTC للمكالمات
    admin/            لوحة تحكم المسير: حظر (هاتف/IP)، سجل تدقيق كامل، حظر غرف
```

## نقاط أساسية قبل الإنتاج (يجب إكمالها قبل الإطلاق الفعلي)
1. **تكامل حقيقي مع مزود دفع مرخّص** في `payment-provider.service.ts` (Chargily/CIB/Stripe) —
   حاليًا مجرد هيكل توضيحي (stub) ولا يعالج أي دفع حقيقي.
2. **رفع الوثائق مباشرة للتخزين السحابي** عبر روابط رفع موقّعة (pre-signed URLs)
   بدل تمريرها عبر الخادم، مع تفعيل التشفير الكامل على مستوى الـ bucket.
3. **خدمة فحص محتوى (moderation)** لرسائل الدردشة والصور/الفيديو المباشر لرصد
   خطاب الكراهية والمحتوى الفاضح تلقائيًا (بالإضافة للمراجعة اليدوية من المسير).
4. **خادم SFU مخصص للوسائط** (يُقترح LiveKit) بدل الاعتماد فقط على P2P WebRTC
   لضمان جودة المكالمات مع عدد أكبر من المستخدمين.
5. **2FA إجباري** لحساب المسير (admin) قبل ربط لوحة التحكم بالإنتاج.
6. **مراجعة قانونية** لسياسة الدفع/الاسترداد وشروط الاستخدام مع محامٍ مختص
   قبل الإطلاق الفعلي (كما ذكرت أنك ستقوم به).
7. الحفاظ على `DB_SYNCHRONIZE=false` وتشغيل `npm run migration:run` عند كل ترقية،
   مع مراجعة الـ migrations الجديدة قبل تطبيقها على الإنتاج. المخطط الأولي مضمّن،
   والمزامنة التلقائية لم تعد مفعّلة افتراضيًا.

## البريد الإلكتروني الخاص بالتطبيق
1. اشترِ نطاقًا (مثل `tabadul-app.com` أو `tabadul.dz`).
2. أنشئ حساب بريد بالنطاق المخصص (Zoho Mail يقدّم خطة مجانية حتى 5
   عناوين بريد، أو Google Workspace للمزايا الكاملة).
3. أنشئ العناوين: `support@yourdomain.com` (للشكاوى) و `admin@yourdomain.com`.
4. اربط سجلات DNS (MX, SPF, DKIM) التي يوفرها المزود عند إضافة النطاق.
5. إذا كانت الخطة المجانية لا تدعم SMTP للإرسال الآلي، استخدم مزودًا
   مخصصًا للإرسال الآلي بجانبها (مثل Zoho ZeptoMail أو SendGrid) واملأ
   `SMTP_HOST/SMTP_USER/SMTP_PASSWORD` في `.env` بمعلوماته.
6. مسار `POST /api/v1/support/complaint` (عام، بدون تسجيل دخول، محدود
   بـ 3 طلبات/ساعة لكل IP) يرسل أي شكوى أو اقتراح مباشرة لصندوق
   `APP_SUPPORT_EMAIL`، بالضبط كما طلبت.

## المصادقة
كل المسارات المحمية تتطلب Header:
```
Authorization: Bearer <JWT_TOKEN>
```
مسارات `/api/v1/admin/*` تتطلب أن يكون دور المستخدم `admin` في قاعدة البيانات
(يُضبط يدويًا مباشرة في قاعدة البيانات لحسابك الشخصي فقط، لا يوجد مسار API لترقية مستخدم لدور admin).
